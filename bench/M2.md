# M2 status: read-only SwiftUI app (2026-11-01)

Build: `app/build.sh` → `app/build/SpaceSense.app` (x86_64, ad-hoc signed, macOS 13+,
Command Line Tools / Swift 5.8 only). Rust core linked as a static library through a
3-function C ABI (`ffi/src/lib.rs`, `app/bridge.h`) that returns JSON.

Screens (all verified by rendering the real window to PNG with `--snapshot DIR`):
Overview (disk bar: home / other data / macOS volumes / free, reclaimable total, FDA
banner, category cards, home breakdown, "System Data" explainer), Developer and
Apps & System (one card per catalog rule: what it is, comes back, exact command, path,
Reveal), Projects (sortable table, filters, search, git, active/stale status, per-artifact
detail), Large Files (sortable table, Reveal), Cleanup preview sheet (read-only plan).

Measured:
- Scan launched from Terminal: 26 s for the full report (scan 19 s + caches + git).
- Idle CPU with a report shown: 0.00 s over 10 s (`sample`); RSS ~200 MB.
- SIGTERM quits, also with the plan sheet open (bug found and fixed: an open sheet
  blocked terminate).

Found while testing:
- **App Nap** throttled a scan started without the window in front (> 80 s). Fixed with
  `ProcessInfo.beginActivity(.userInitiated)` for the length of the scan.
- **Privacy (TCC) dialogs block the scan.** Launched as an app (not from Terminal), the
  first read of Desktop / Documents / Downloads / other apps' containers shows a macOS
  "would like to access" dialog and the `openat` blocks until it is answered (11 worker
  threads seen waiting). The app now reports a phase and shows "Waiting for macOS
  permission" with a Full Disk Access button when reading stalls for 4 s.
  Not yet verified on screen (would pop the dialogs again; owner's call).
- Ad-hoc signatures change on every rebuild, so TCC answers don't carry over between
  builds. A stable signing identity (M4, Developer ID) fixes that.

Open for M2 "done": owner runs the app, answers or grants access, and confirms the
screens explain where the 383 GB went. Lists don't stream during the scan (counters do);
results appear when the report completes (~25 s).

## Folder browser (added 2026-11-01, owner request)

"Folders" screen: drill into any folder of the last scan (tree kept in Rust memory,
`ss_folder` FFI; no rescan). Each subfolder shows size, owning app (resolved from bundle
id or folder name via NSWorkspace, with icon; "app not installed (may be leftover)" when a
bundle id has no app), and a verdict: Cache / Rebuilds / Review / Don't delete with the
reason. Catalog rules and project build folders override the generic ~/Library
conventions (core/src/explain.rs). Overview's "Where your home folder goes" rows open it.
Full Disk Access: apps never add themselves to the list; the button now also reveals the
app in Finder and the banner says to click + / drag it in, then relaunch.

## Cloud storage (2026-11-01, owner decision)

With Full Disk Access the scan entered iCloud Drive and blocked opening an iCloud-only
package (`…/iCloud~com~apple~iBooks/Documents/*.epub`), which made macOS start
downloading it. Owner decided cloud storage isn't worth scanning: `~/Library/Mobile
Documents` and `~/Library/CloudStorage` are never entered (`ScanOptions::skip`, shown as
"not scanned: cloud storage"). As a second layer the scan sets
`setiopolicy_np(IOPOL_TYPE_VFS_MATERIALIZE_DATALESS_FILES, OFF)` and skips SF_DATALESS
folders, so nothing anywhere can trigger a cloud download.
