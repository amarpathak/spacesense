# M0 results: engine spike (2026-10-31)

Machine: MacBook Pro 2019, Intel i7-9750H (6 cores / 12 threads), macOS 26.5.2, APFS.
`~` = 4.18 M files, 589 k dirs, 257 GiB allocated. Numbers are "warm" (run straight after
another scan); see the caveats below.

## Accuracy: met

| Tool | Total (KiB) | vs `du -skx` |
|---|---|---|
| `du -skx ~` | 269 500 348 | — |
| spacesense (bulk) | 269 528 396 | +0.010 % |
| spacesense (stat) | 269 526 092 | +0.010 % |
| diskus | 269 502 316 | +0.001 % |

The runs were minutes apart on a live disk, so a 0.01 % (27 MB) drift is expected. On
static trees (`~/.cargo`, `~/.rustup`, the 23 GB Yarn cache) all three totals equal `du`
**exactly**, and the 9 fixture tests (`cargo test`) check equality with `du -skx` on both
backends: hard links (counted once), sparse file (`mkfile -n`), APFS clone (`cp -c`,
summed like `du`), symlink loops, `chmod 000` dir, 300-deep nesting, 5000-entry dirs
(several `getattrlistbulk` batches), mtime propagation.

351 dirs are unreadable without Full Disk Access (EPERM: `~/Library/Caches/com.apple.Safari`,
`CloudKit`, `Application Support/CloudDocs`, …). `du` skips the same ones.

## Speed: target not met yet

**Quiet re-run (2026-11-01 00:18, load avg ≈ 2.5):**

| Tool | Time on `~` | Total |
|---|---|---|
| **spacesense (bulk, 12 threads)** | **19.6 / 19.8 s** | 273 643 524 KiB |
| spacesense (bulk, 8 threads) | 23.3 s | |
| spacesense (bulk, 6 threads) | 26.0 / 26.3 s | |
| diskus | 29.1 / 29.9 s | 273 643 436 KiB (equal to ours within 88 KiB) |
| dust | 38.1 s | |

So 12 threads (one per logical CPU) is the right default. SpaceSense is ~1.5× faster than
diskus and ~2× faster than dust, but still 2× over the < 10 s warm target.

**First run (2026-10-31, machine heavily loaded):**

| Tool | Time | Notes |
|---|---|---|
| **spacesense (bulk)** | **20–30 s** | 20.0 s on the first run; 26.8 / 29.6 / 29.5 s with load avg ≈ 20 |
| spacesense (stat) | 48 s | readdir + fstatat |
| diskus | 26.3 s | |
| dust | 43.5 s | |
| du -skx | 185 s | |

- `getattrlistbulk` is **1.6–1.8× faster** than readdir+lstat on the same walker. Keep it as
  the default, with stat as the fallback (also used automatically on ENOTSUP).
- SpaceSense is 7× faster than `du` and level with diskus, but **misses the < 10 s warm target**.
- Time is almost all kernel: user 5 s, sys 220 s across 12 threads. Adding threads adds sys
  time without adding speed (2 threads: 98 s; 6: 26–31 s; 12: 24–29 s).
- Likely cause: `kern.maxvnodes` = 263 k, against 4.8 M entries, so each scan recycles
  the vnode cache (31 M recycles counted) and is never truly warm. Switching to `openat`
  relative to a held parent fd helped small trees (`~/.npm` 1.4 → 1.1 s) but not `~`.
- The machine was heavily loaded during the benchmarks (other sessions; load avg 9–21 on 12
  threads), so all timings are pessimistic and noisy.
